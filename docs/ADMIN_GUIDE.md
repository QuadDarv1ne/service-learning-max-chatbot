## Ваша роль

Как администратор системы вы отвечаете за:
- ✅ Первичную установку и настройку бота
- ✅ Подключение к MAX Bot API (токен, webhook)
- ✅ Регулярный мониторинг здоровья системы
- ✅ Бэкап базы знаний и логов
- ✅ Реагирование на алерты (ошибки MAX API, неудачные входы)
- ✅ Смену пароля админки
- ✅ Помощь сотрудникам программы в работе с базой знаний

Вы **не** занимаетесь наполнением базы знаний — это делают сотрудники программы через [Руководство сотрудника](./STAFF_GUIDE.md).

## Первичная настройка

См. подробное руководство в [DEPLOYMENT.md](./DEPLOYMENT.md). Кратко:

1. **Установить приложение** на сервере (или локально для тестирования)
2. **Сменить `ADMIN_PASSWORD`** в `.env` (минимум 12 символов)
3. **Применить схему БД**: `bun run db:push`
4. **Заполнить базу**: `bun run scripts/seed.ts`
5. **Запустить**: `bun run dev` (или systemd сервис в продакшене)
6. **Зарегистрировать бота в MAX** — создать и верифицировать профиль, создать бота на [Портале для бизнеса MAX](https://business.max.ru/self) и получить токен (см. [«Токен бота MAX»](#токен-бота-max))
7. **Внести настройки в админ-панель**: токен, webhook URL
8. **Подписать webhook** через кнопку в Настройках
9. **Проверить бота** — кнопка «Проверить бота» должна показать имя и ID
10. **Зарегистрировать команды** — `/start` и `/help` появятся в автодополнении MAX

## Регулярные задачи

### Ежедневно (5 минут)

1. **Проверить здоровье системы**
   - Откройте админку → «Настройки» → карточка «Здоровье системы» в самом верху
   - Все 4 индикатора должны быть 🟢
   - Метрики за 24ч: ошибки MAX API должны быть 0 (красным если >0)
   - Avg отклик 24ч — обычно < 1000 мс, если значительно больше — есть проблема

   Или через curl (для uptime-мониторинга):
   ```bash
   curl https://your-domain.ru/api/health
   ```

2. **Проверить бейджи в навигации** (если красные — нужно вмешательство):
   - «Запросы без ответа» — если >5, пора пополнять базу (но это делает сотрудник)
   - «Логи обращений» — если >0 красный, есть проблемы с MAX API
   - «Журнал действий» — если >0 красный, есть неудачные admin-действия

### Еженедельно (15 минут)

1. **Открыть раздел «Аналитика»**
   - Период: 7 дней
   - Проверить воронку: faqMatchRate должен быть 70%+
   - Если LLM-обработка >20% — база знаний не покрывает вопросы (сообщить сотрудникам)
   - Если offTopicRate >15% — возможно, пользователи не понимают, что бот только по программе

2. **Открыть раздел «Журнал действий»**
   - Отфильтровать `ok=false`
   - Если есть неудачные попытки входа (`login_failed`) с одного IP — возможно, атака

3. **Бэкап базы знаний**
   - Раздел «Настройки» → «Экспорт базы знаний»
   - Сохранить JSON-файл в надёжное место (например, в Git или облачное хранилище)

### Ежемесячно (30 минут)

1. **Полный бэкап SQLite базы**:
   ```bash
   sudo systemctl stop max-bot
   cp /opt/max-bot/data/custom.db /backup/custom-$(date +%Y%m%d).db
   sudo systemctl start max-bot
   ```
   Или настройте cron на автоматический бэкап.

2. **Архивация логов**
   - Раздел «Логи обращений» → «Экспортировать в CSV» за весь месяц
   - Сохранить в архив

3. **Проверка uptime сервера**
   - Если используете uptime-мониторинг (Uptime Robot, Better Stack) — посмотрите отчёт за месяц
   - Если uptime < 99% — нужно исследовать причины падений

## Безопасность

### Пароль админки

- **Минимум 12 символов**
- Содержит заглавные и строчные буквы, цифры, спецсимволы
- Не используется нигде больше
- Хранится в `.env` файле, который **не коммитится в Git**
- Меняется раз в 3 месяца

Примеры хорошего пароля:
- `Xy7$mB2nQ9!pL4vR`
- `M@c5vQ8zF3kR2nB7`

⚠️ Демо-пароль `admin123` **только для тестирования**.

### Логи неудачных входов

Все попытки входа (успешные и неудачные) логируются в `AdminActionLog`. Чтобы проверить:

1. Раздел «Журнал действий»
2. Фильтр: `action = login_failed`
3. Если видите 5+ неудачных попыток с одного IP-хеша за короткое время — это может быть атака перебором

Защита от перебора на уровне приложения пока не реализована. Если атака обнаружена:
- Измените `ADMIN_PASSWORD` в `.env`
- Перезапустите сервис
- (Опционально) заблокируйте IP на уровне Caddy/Nginx

### Токен бота MAX

**Где получить.** Токен выдаётся на **Портале для бизнеса MAX** — [business.max.ru/self](https://business.max.ru/self):

1. Раздел **«Чат-боты»** → выберите бота → **⋮** → **«Настройки»**
2. Блок **«Чат-бот»** → поле **«Токен доступа»** → **значок копирования**

Токен формируется только после успешной модерации бота (до 48 часов по рабочим дням). То же доступно через мини-приложение [«MAX для бизнеса»](https://max.ru/business_bot?startapp).

**Где хранится в проекте:**
- В `BotSetting` в SQLite базе (задаётся через админку: «Настройки» → «Токен бота»)
- Резервно — в переменной окружения `MAX_BOT_TOKEN` (используется, только если в БД пусто)
- Не включается в JSON-бэкап базы знаний (по соображениям безопасности)
- Виден в админке только как `••••••••••••••••1234` (последние 4 символа)

**Проверка:** кнопка **«Проверить бота»** в разделе «Настройки» должна показать имя и ID. Или вручную:
```bash
curl -H "Authorization: <токен>" https://platform-api2.max.ru/me
```

**При утечке / компрометации:**
1. На Портале для бизнеса: **«Чат-боты»** → **⋮** → **«Настройки»** → **значок обновления** рядом с токеном
2. Скопируйте новый токен и вставьте его в админке приложения («Настройки» → «Токен бота» → «Сохранить»)
3. При необходимости оформите webhook-подписку заново (старый токен перестаёт действовать)

### HTTPS

⚠️ **MAX не принимает HTTP webhook с мая 2025**. Ваше приложение должно быть доступно по HTTPS с сертификатом от доверенного CA:
- Let's Encrypt (бесплатно, через Caddy/Nginx/Certbot)
- Сертификаты Минцифры РФ (подходят для российских доменов .ru/.рф)
- Коммерческие сертификаты (DigiCert, GeoTrust, etc.)

Самоподписанные сертификаты **не работают**.

### База данных

- SQLite база в файле (по умолчанию `db/custom.db`)
- Доступ к файлу = полный доступ к данным. Защитите права доступа:
  ```bash
  chmod 600 /opt/max-bot/data/custom.db
  chown maxbot:maxbot /opt/max-bot/data/custom.db
  ```
- Регулярный бэкап файла — обязателен (см. выше)

## Мониторинг и алерты

### Health endpoint

`GET /api/health` возвращает JSON со статусом системы. Используйте в uptime-мониторинге:

**Uptime Robot** (бесплатно):
1. Создайте новый монитор типа HTTP(s)
2. URL: `https://your-domain.ru/api/health`
3. Интервал: 5 минут
4. Keyword monitor: ищите `"ok":true` — если нет, алерт
5. Настройте уведомления (email, Slack, Telegram)

**Better Stack**:
1. Создайте heartbeat monitor
2. Method: GET
3. URL: тот же
4. Response validation: JSON contains `"ok": true`
5. Setup integration для алертов

### Бейджи в навигации

В админ-панели рядом с разделами показываются цветные бейджи:
- 🟡 жёлтый — есть элементы, требуют внимания
- 🔴 красный — критично (>5 элементов)

Бейджи обновляются каждые 60 секунд автоматически.

### Что делать при красных бейджах

| Где красный | Что значит | Действие |
|-------------|------------|----------|
| «Запросы без ответа» >5 | Пользователи задают вопросы, на которые нет ответа в базе | Сообщить сотрудникам программы — они добавят ответы через [STAFF_GUIDE.md](./STAFF_GUIDE.md) |
| «Логи обращений» >0 (maxApiErrors) | MAX API не принимает сообщения | Проверить токен (Настройки → «Проверить бота»), webhook подписку, сеть |
| «Журнал действий» >0 (auditFailures) | В админке были неудачные действия | Открыть Журнал, отфильтровать `ok=false`, посмотреть ошибки |

## Бэкап и восстановление

См. подробное руководство в [DEPLOYMENT.md → Бэкап и восстановление](./DEPLOYMENT.md#бэкап-и-восстановление).

Кратко:

### Что бэкапить

| Что | Как часто | Размер | Назначение |
|-----|-----------|--------|------------|
| База знаний (JSON) | Еженедельно | ~25 KB | Восстановление базы ответов |
| SQLite база (.db) | Ежедневно + перед обновлениями | ~50-500 KB | Полное восстановление (с пользователями, логами, настройками) |
| Логи обращений (CSV) | Ежемесячно | Зависит от активности | Отчётность, аудит |
| Журнал admin-действий (CSV) | Ежемесячно | ~10 KB | Аудит безопасности |
| `.env` файл | При изменении | ~200 bytes | Восстановление настроек (токен в БД!) |
| Архив проекта (tar.gz) | При обновлении | ~200 KB | Откат к старой версии |

### Где хранить

- Локально на сервере: `/backup/` (но не в той же директории, что приложение)
- Внешнее хранилище: S3-совместимое (Yandex Object Storage, VK Cloud, AWS S3)
- Git-репозиторий (для базы знаний JSON — она текстовая)
- Облачная папка (Yandex Disk, Google Drive) через rclone

### Тестирование восстановления

⚠️ Раз в квартал — обязательно проверить, что бэкап восстанавливается:
1. Развернуть на тестовом сервере
2. Импортировать JSON базы знаний
3. Восстановить SQLite из бэкапа
4. Проверить health endpoint
5. Если всё ОК — бэкап надёжный

## Управление пользователями

### Пользователи бота (MAX users)

Обычные пользователи (педагоги, представители организаций) — не требуют управления:
- Они сами находят бота в MAX по никнейму
- Записи о них создаются автоматически при первом обращении
- Их профиль (имя, фамилия, username) обновляется при каждом обращении

### Просмотр истории конкретного пользователя

1. Раздел «Дашборд» → блок «Недавние пользователи» — клик по имени
2. Или раздел «Логи обращений» → клик по имени в любой строке
3. Или через API: `GET /api/users/{maxUserId}`
4. Откроется модальное окно с диалогом в стиле мессенджера

В диалоге видно:
- Все сообщения в хронологическом порядке
- Бейдж источника каждого ответа (search, llm, fallback, off_topic, faq)
- Время обработки (durationMs)
- Ошибки MAX API (если были) — красная подсветка

### Блокировка пользователей

Функция пока не реализована. Если пользователь злоупотребляет:
- Можно заблокировать через [Портал для бизнеса MAX](https://business.max.ru/self)
- Или реализовать middleware в `/api/max/webhook` с проверкой MaxUser.id в чёрном списке

### Анонимизация

IP-адреса в `AdminActionLog` хранятся как SHA-256 хеши (16 символов), не raw. Это значит:
- Нельзя узнать IP по хешу (односторонняя функция)
- Можно проверить, что два действия с одного IP — сравнивая хеши
- Соответствует требованиям GDPR/152-ФЗ

## Когда что-то сломалось

См. [TROUBLESHOOTING.md](./TROUBLESHOOTING.md) для детального разбора.

### Самые частые проблемы

1. **Бот не отвечает на сообщения в MAX**
   - Проверить: Настройки → «Проверить бота» → должен вернуть имя
   - Проверить: «Подписка активна» (не «Webhook не подписан»)
   - Проверить: health endpoint → `webhookSubscribed: true`
   - Проверить: Раздел «Логи» → доходят ли входящие сообщения?

2. **Ошибки MAX API в логах (красные бейджи)**
   - HTTP 401 — невалидный токен (пересоздать в платформе MAX)
   - HTTP 429 — превышен лимит 30 rps (много одновременных пользователей)
   - HTTP 503 — MAX API временно недоступен

3. **Бот отвечает не по теме**
   - Скорее всего, off-topic фильтр пропускает запросы в LLM
   - Проверить: Раздел «Аналитика» → `offTopicRate`. Если >15% — нужно скорректировать STRONG/WEAK terms в `lib/llm.ts`
   - Или: больше fallback → `fallbackRate > 5%` → пополняйте базу знаний

4. **База знаний исчезла**
   - Проверить: было ли выполнено `bun run scripts/seed.ts` (он **перезаписывает** базу)
   - Восстановить из бэкапа: Настройки → «Импорт базы знаний»

5. **Не могу войти в админку**
   - Проверить: пароль в `.env` (`ADMIN_PASSWORD`)
   - Если забыли — изменить в `.env` и перезапустить сервис
   - Cookie живет 7 дней, потом нужно войти снова

### Когда обращаться за помощью

- К федеральной команде программы: info@dobro.ru (в теме «Обучение служением»)
- Сpecified в MAX: [dev.max.ru/docs](https://dev.max.ru/docs) или через бота `MAX для бизнеса`

## Чек-лист нового администратора

При передаче обязанностей новому администратору, убедитесь что:

- [ ] Знает URL админ-панели (https://your-domain.ru)
- [ ] Знает пароль (или может сбросить через .env)
- [ ] Имеет SSH-доступ к серверу
- [ ] Знает где лежит `.env` файл
- [ ] Знает как сделать бэкап и восстановление
- [ ] Прочитал [DEPLOYMENT.md](./DEPLOYMENT.md), [ADMIN_GUIDE.md](./ADMIN_GUIDE.md) (этот документ), [TROUBLESHOOTING.md](./TROUBLESHOOTING.md)
- [ ] Знает куда писать при проблемах (info@dobro.ru)
- [ ] Понимает, что бэкап базы знаний — это **его** ответственность
- [ ] Знает как переключить период в Аналитике (7d / 30d / 90d / all)
- [ ] Подключил uptime-мониторинг на /api/health
